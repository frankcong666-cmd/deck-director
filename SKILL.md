# Deck Director

Turn a raw topic, outline, document, product, or idea into a finished presentation with a coherent point of view. Treat the deck as one directed experience: argument, spoken delivery, visual system, and layout must reinforce one another.

## Operating model

Use the workflow below as a reproducible SOP. Keep it proportional: a small edit can enter at the relevant phase, while a new deck should normally begin with the brief.

1. **Brief** — establish audience, objective, language, speaking time, slide count, source material, and the user's visual preferences. State material assumptions before they shape the work.
2. **Story** — form one central claim and a slide-by-slide narrative. Draft or confirm the spoken script early, especially for a timed talk.
3. **Art direction** — translate the requested mood into composition, typography, color, imagery, and pacing. Offer a few genuinely different directions when the visual brief is open; do not assume a default style.
4. **Evidence and assets** — decide what requires real screenshots, data, diagrams, source images, or generated conceptual visuals. Keep evidence accurate and traceable.
5. **Production** — build an editable deck that matches the selected visual system and gives each slide one clear job.
6. **Critique and revision** — inspect rendered slides, diagnose specific problems, and iterate on hierarchy, alignment, readability, image crop, and narrative flow.
7. **Delivery** — validate the requested output, provide the final file, speaker notes or script when requested, and note any limitation that affects use.

Read [the deck production SOP](references/deck-production-sop.md) for the detailed workflow. Read [the story and visual guide](references/story-and-visual-guide.md) when developing a narrative or a visual direction.

## Direct the story before the pages

Do not begin by filling slide templates. First identify the decision, lesson, recommendation, or change in understanding that the audience should carry away. Build a narrative with a clear opening, development, and ending; use the slide order that best serves that purpose.

For a spoken presentation, write prose that the presenter can say naturally. Keep on-slide language shorter than the script, and use timing to decide whether to cut, combine, or add detail.

## Adapt to the user's taste

The user's stated taste outranks a house style. Ask for or infer preferences such as editorial, minimal, cinematic, playful, academic, premium, technical, warm, restrained, or bold. Use references the user supplies as visual evidence, not merely inspiration.

When the user has not chosen a visual direction, show a small set of distinct options that vary in composition and image treatment as well as palette. Once selected, preserve the resulting visual grammar across the deck. Do not make every slide identical; use variation to support pacing while keeping typography, spacing, and color relationships coherent.

## Keep claims and visuals honest

Use real product screenshots, data, documents, or primary sources when the deck makes factual claims about them. Use generated visuals for metaphors, atmosphere, transitions, or clearly conceptual scenes. Do not present a generated UI, chart, or product view as proof of an actual interface or event.

Prefer a small number of high-quality visual elements over decorative clutter. Preserve meaningful negative space, put text where the image has genuine room for it, and never obscure essential evidence with an opaque overlay merely to create copy space.

## Make revision efficient

Treat user feedback as a design diagnosis. Change the requested problem first and preserve approved work. When the request is only for an asset, return only the asset; when it is only for a slide edit, do not redesign the rest of the deck.

Before delivery, render and visually inspect the deck. Check hierarchy, text fit, crop, contrast, alignment, consistency, and whether the conclusion feels earned. Keep the final PowerPoint editable unless the user explicitly asks for a flattened format.
